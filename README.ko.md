# CodeGrove — 무엇이고, 얼마나 잘 되는가

*[English](README.md)*

**CodeGrove는 코드베이스를 질의 가능한 지식 그래프로 만든다.** 코딩 에이전트에게 파일을 던져
주고 뒤지게 하는 대신, "버그는 이 함수에 있다"고 바로 알려주기 위해서다.

이 저장소는 그 프로젝트의 **증거 쪽 절반**이다. 평가 방법, 측정한 모든 수치, 실패한 실험을
담았다. 엔진 소스는 비공개다. 이유는 [아래](#엔진-소스를-여기-두지-않은-이유)에 적었다.

**핵심 결과다. 실제 SWE-bench Django 이슈 99건을 재료로 썼다. 시스템이 첫 번째로 내놓는
함수가 정답인 비율은 73.7%다. 상위 10개 안에 정답이 들어오는 비율은 93.9%다.**

---

## 1. 무엇인가

grep은 문자열을 찾는다. 임베딩은 비슷해 *보이는* 코드를 찾는다. 둘 다 관계를 모른다.
무엇이 무엇을 호출하는지 모른다. 이 변경이 무엇을 깨뜨리는지도 모른다. 이 심볼이 어느 모듈
소속인지도 모른다. CodeGrove는 그 관계를 한 번 만들어 두고 계속 최신으로 유지한다.

```text
소스 저장소  (9개 언어: Python, Java, Kotlin, Scala, JS, TS, C/C++, Go, Rust)
      │
      ▼  Tree-sitter 파서
언어 중립 엔티티와 관계
      │   파일 · 모듈 · 클래스 · 함수 · 호출 · 임포트 · 상속 · 출처
      ▼
그래프 저장소  (Neo4j / Memgraph → 이후 PostgreSQL + pgvector로 이전)
      │
      ├── 임베딩          Ollama · OpenAI 호환 · UniXcoder
      ├── 커뮤니티 탐지    Leiden / Louvain
      ├── DB 스키마 적재   MariaDB / MSSQL 스키마를 같은 그래프에
      ├── 증분 동기화      git diff 기반. 바뀐 것만 다시 파싱한다
      └── MCP 서버        코딩 에이전트가 직접 질의한다
      │
      ▼
로컬라이제이션 파이프라인  ── 이슈 본문 ──► 함수 FQN 순위 목록
   1단계  하이브리드 검색(벡터 + 그래프)으로 후보 파일 추출
   2단계  로컬 교차 인코더 재랭커(Qwen3-Reranker-0.6B, llama.cpp)
   3단계  LLM 리스트와이즈 재랭킹으로 최종 함수 순위 결정
```

> **약어 풀이** — FQN(Fully Qualified Name)은 `파일경로.클래스.메서드` 형태의 전체 이름이다.
> MCP(Model Context Protocol)는 에이전트가 외부 도구를 호출하는 규약이다.

**이 시스템이 푸는 문제.** 이슈를 고치라고 받은 코딩 에이전트는 보통 탐색에 컨텍스트를 태운다.
파일을 나열하고, grep하고, 열어보고, 다시 반복한다. 처음 여는 파일이 이미 정답 함수라면 그
반복이 통째로 사라진다. 그래서 이 프로젝트는 파일 단위도 top-10도 아닌 **함수 단위 top-1**을
최적화한다.

## 2. 무엇을 어느 규모로 만들었나

**1인 개발이다.** AI 에이전트를 개발팀처럼 오케스트레이션해 설계와 구현을 직접 했다.
2026년부터 진행 중이다.

| 항목 | 값 |
| --- | --- |
| **운영 중인 그래프 규모** | **45만 5,540 노드 · 113만 1,482 엣지 · 18만 1,464 임베딩** (저장소 12개) |
| **대상 코드베이스** | 비공개 멀티레포 폴리글랏. C++ · Java · Kotlin · TypeScript를 한 그래프에 |
| **파싱 언어** | 9개 |
| **엔진 테스트** | 1,925개 |
| **에이전트 표면** | MCP 서버, 내장 도구 20종 (별도 에이전트용 서버 추가) |
| **백엔드 이전** | 인메모리 그래프DB → PostgreSQL + pgvector 무손실 이전. **51 PASS / 0 FAIL**, 차등 동등성 **255/256**, 벡터 **recall@10 0.955** |

수치가 기대는 기술 판단 세 가지를 밝힌다.

- **Cypher 가변 길이 탐색을 PostgreSQL `WITH RECURSIVE` CTE로 대체했다.** 필요한 것은 그래프
  *엔진*이 아니라 *엣지 사실*이라고 전제를 다시 잡았다. 이 판단 하나로 라이선스 부담, 메모리
  천장, 운영 부담을 한꺼번에 걷어냈다.
- **이전 작업은 차등 동등성 하니스 뒤에서 진행했다.** 같은 코드를 두 백엔드로 띄우고 결과를
  비교한다. 이 하니스가 운영 투입 전에 실제 버그를 잡았다. 직렬화 크래시, collation 불일치,
  엣지 오삭제였다.
- **평가를 스크립트가 아니라 하나의 서브시스템으로 만들었다.** 이 저장소의 나머지가 그 결과다.

## 3. 얼마나 잘 되는가

`cm99`는 실제 [SWE-bench](https://www.swebench.com/) Django 이슈 99건이다. 각 이슈에는 공식
수정 패치가 실제로 바꾼 **함수**가 정답으로 붙어 있다. 레퍼런스 실행 `sonnet5_both_max`,
2026-07-01 측정값이다.

| | top-1 | top-3 | top-10 |
| --- | :---: | :---: | :---: |
| **함수 단위** (n=99) | **73.7 %** | **86.9 %** | **93.9 %** |
| 파일 단위 (n=99) | 77.8 % | 84.8 % | 87.9 % |

cm99 정식 실행 9회 전체에서 **함수 단위 top-1은 0.727 ~ 0.849** 범위다. 저하된 구성 1건만
0.232로 떨어진다. 전체 최고 측정값은 **0.860**이다.

**[`data/localization-runs.csv`](data/localization-runs.csv)에 채점한 133개 스트림이 한 줄씩
들어 있다.** 이 문서의 모든 숫자는 그 파일의 셀이다.

### "함수 단위 top-1"의 정확한 뜻

> 이슈 본문을 준다. 시스템에 함수 순위 목록을 요청한다. **맨 앞에 온 함수가 공식 수정이 실제로
> 바꾼 함수인가?**

정답 *파일*이 아니라 정답 *함수*를, 한 번에 맞히는 비율이다. 정답 라벨은 SWE-bench 패치에서
뽑는다. 변경된 각 줄을 **base commit 시점** 소스에서 감싸는 함수로 해석하고,
`파일경로.클래스.메서드` 형태로 기록한다. 공개 데이터만으로 도출할 수 있다.

### 암기가 아니다

cm99는 공개 데이터이고 모델 학습 데이터에 들어갈 만큼 오래됐다. 그래서 같은 파이프라인을
**`fresh-2026`에서 다시 측정했다. judge의 학습 컷오프 이후에 머지된 Django 풀 리퀘스트(PR) 29건**
이다.

함수 단위 top-1은 **0.724 ~ 0.828**이 나왔다. cm99의 0.727 ~ 0.849와 같은 대역이다. 13개
구성을 [`data/fresh-2026-judges.csv`](data/fresh-2026-judges.csv)에 담았다.

*단, n=29라 1건이 3.4%p를 움직인다. 이 데이터는 암기가 지배적 설명이 아님을 보일 뿐이다.
judge 사이의 작은 차이까지 가르지는 못한다.*

## 4. 어떻게 측정했나

측정을 부수 작업이 아니라 산출물로 다뤘다.

- **정답셋을 감사하고 다시 동결했다.** 초기 라벨은 감사한 41건 중 **37건이 오염**돼 있었다.
  패치를 적용한 *뒤*의 소스로 함수를 해석하고 있었다. base commit 기준으로 재구축하고
  SHA-256으로 동결한 다음 **전 스트림을 재채점했다.** 같은 실행의 점수가 0.209에서 0.737로
  바뀌었다. 여기서 규칙을 얻었다. **저장된 지표 필드는 결과가 아니다.**
- **눈대중 대신 유의성 검정을 썼다.** 대응표본 이진 결과에는 McNemar를, top-k 신뢰구간에는
  paired bootstrap을 적용했다.
- **실험을 사전등록했다.** 셀을 돌리기 전에 가설, 지표, 판정 규칙을 먼저 적었다. 실행한 셀은
  전부 보고한다는 규칙을 함께 뒀다.
- **천장을 찾아냈다.** 상위 4개 judge 구성은 **통계적으로 구별되지 않는다**(McNemar p=0.607,
  bootstrap 신뢰구간이 0을 포함). 즉 0.82 ~ 0.85가 이 파이프라인의 selection 천장이다.
  "우리 수치가 제일 높다"는 주장은 성립하지 않는다.

## 5. 무엇이 안 됐나

실패한 실험을 공개한다. 현재 기본값의 근거가 실패 기록이기 때문이다. 이긴 것만 싣는 문서는
벤치마크 문서가 아니다.

oracle 분석 결과 병목은 **검색이 아니었다.** 정답 함수가 후보 풀에 들어오는 비율은 82~83%인데
top-1은 그보다 17 ~ 25%p 낮다. 손실은 **형제 함수 변별**에서 난다. 이미 맞게 고른 파일 안에서
비슷비슷한 함수 여러 개 중 하나를 고르는 단계다.

이 병목을 뚫으려고 여섯 가지를 사전등록해 검정했다. **전부 노이즈 내 무효였다.** 검정한 여섯
가지는 다음과 같다.

1. judge 프롬프트 재구성
2. 호출 방향 관계 주입
3. value-provenance 재랭킹
4. 변형 합의 selector
5. 이슈 truncation 해제
6. temperature 고정

그중 하나가 승리보다 쓸모 있는 것을 드러냈다. judge가 기본 온도에서 **22.8% 비결정적**이었다.
이 노이즈가 그동안 모든 A/B의 효과 크기를 삼키고 있었다. `temperature=0`으로 고정하자 재현성이
69.6%에서 91.3%로 올라갔다. 다만 **정확도는 그대로였다.** 통계적 검정력을 얻는 레버지 품질
레버가 아니다. 온도를 고정한 뒤 여섯 개입을 다시 검정했는데 여전히 무효였다. 그래서 결론을
믿을 수 있다. **ranking prior는 judge 모델에 내재한 성질이고 프롬프트로 움직이지 않는다.**

**정확도 순위보다 중요한 비용 발견이 있다.** `grok-4.5`를 `effort=high`로 쓰면 중앙 지연
**2.5초**, 인스턴스당 **$0.015**로 0.759가 나온다. 최고 구성은 64초에 두 배 비용으로 0.828이다.
7%p를 얻으려고 지연을 **26배** 치르는 셈이다. 애초에 상위 구성들이 통계적으로 동급이므로,
**judge는 정확도가 아니라 비용과 지연으로 고르는 것이 맞다.**

## 6. 정정 안내

2026-08-09와 08-10에 이 대표 수치를 **잘못 철회**하고 0.209 / 0.330 / 0.495로 바꿨다. 그 철회는
**2026-08-10에 무효화했다.** 원래 수치가 맞았다.

원인은 이렇다. 철회할 때 실행 JSON에 저장된 레거시 `fn_top1` 필드를 읽었다. 그 필드는 폐기된
오염 정답셋(`gold v1`) 기준 점수다. 원본 예측을 `gold v2`로 다시 채점하면 0.737 / 0.869 /
0.939가 나온다.

오류와 그 무효화를 모두 [`BENCHMARKS.md`](BENCHMARKS.md#correction-log)에 남겼다. 지우지 않았다.

## 엔진 소스를 여기 두지 않은 이유

CodeGrove는 상용화를 검토 중인 비공개 프로젝트다. 벤치마크 주장을 반증 가능하게 만드는 것은
**방법론과 실행 원자료**이고, 둘 다 여기 있다. 정답 라벨 도출 규칙까지 적어 두었으니 제3자가
채점을 다시 구현할 수 있다. 엔진 공개는 그 목적에 필요하지 않고, 되돌릴 수도 없다.

## 한계를 밝힌다

- 점수는 judge 모델과 effort 설정에 따라 움직인다. cm99에서 0.232 ~ 0.849까지 벌어진다.
  구성을 빼고 숫자만 말하면 의미가 없다.
- cm99는 Django 99건 부분집합이지 SWE-bench 전체가 아니다.
- 이 벤치마크에서는 인덱스 없이 `Read`/`Grep`/`Glob`만 쓴 프런티어 모델이 더 높다. 같은
  인스턴스에서 0.75(fresh) / 0.80(오염 포함)로 파이프라인을 앞선다. Django는 작고 공개돼 있으며
  구조가 정연한 저장소다. 코드 그래프의 이점이 가장 적게 나오는 조건이다. 이 비교도
  [`EXPERIMENTS.md`](EXPERIMENTS.md#campaign-6--the-unflattering-comparison)에 실었다.
- 이 수치는 한 시점의 한 파이프라인을 특징짓는 값이다. 리더보드 점수가 아니다.
